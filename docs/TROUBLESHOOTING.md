# 故障排查

建议先执行：

```sh
m-ui status
m-ui logs
```

## 电视无法连接

表现：日志出现“无法连接电视 ADB”或应用列表无法加载。

依次检查：

1. 运行 `m-ui`，通过菜单第 `1` 项确认电视 IP 是否正确。
2. 路由器能否 `ping` 到电视。
3. 电视是否连接了访客 Wi-Fi，路由器是否开启了 AP/客户端隔离。
4. TCP `5555` 和 `6095` 是否可访问。
5. 电视重启或升级后，ADB 开关是否被关闭。

如果有线电脑能访问电视、无线设备不能访问，即使 SSID 的“隔离客户端”开关已关闭，也要继续检查访客网络、VLAN、桥接接口、交换机端口隔离和防火墙转发规则。

## ADB 一直未授权

手动触发连接：

```sh
/usr/lib/m-ui/m-adb -s 192.168.1.100:5555 connect 192.168.1.100:5555
```

将地址改为电视实际 IP，然后观察电视屏幕。若以前点过拒绝，可在电视开发者设置中撤销 USB/ADB 调试授权，再重新连接。

必要时可以重新生成路由器的 ADB 身份：

```sh
m-ui stop
mv /etc/m-ui/adbkey /etc/m-ui/adbkey.old
m-ui start
```

这会让电视把路由器视为新设备，需要重新确认授权。确认一切正常后再自行删除备份。

## 能列出应用，但亮屏后没有启动

1. 查看日志中是否出现“检测到电视由息屏进入亮屏”。
2. 确认已经通过菜单设置应用，`m-ui status` 不应显示“未设置”。
3. 确认等待期间电视没有再次息屏。
4. 直接在菜单中重新选择一次应用，排除包名已经变化。
5. 使用本地 Web 遥控器或 6095 URL 手动测试 `startapp` 接口。

如果日志只显示初始状态 `ON`，说明 m-ui 启动时屏幕已经亮着，且 ADB 一开始就可用。它不会把这种初始 `ON` 当成一次亮屏事件；先让电视息屏，再重新亮屏测试。ADB Keeper 恢复 ADB 时观察到的 `ON` 会被当作冷启动事件。

## 设置 3 秒，但约 5 秒才启动

这是正常的。m-ui 默认每 2 秒读取一次屏幕状态，所以实际时间为：

```text
0～2 秒检测等待 + 3 秒启动延迟 ≈ 3～5 秒
```

可以修改 `/etc/m-ui/config` 中的 `POLL_INTERVAL`，但不建议在性能有限的路由器上设为小于 1 秒。

## 电视断电时是否会拖垮路由器

不会。普通监控的网络连接都有超时时间。确认电视离线后的前 120 秒，m-ui 每 1 秒开始一轮尝试，优先抓取开机早期 ADB 窗口；一次网络操作超时时实际间隔会略长。之后退回每 30 秒一次的低频检查。它不会创建越来越多的进程，也不会通过 `6095` 反复唤起电视应用。

## 日志会不会写满存储

`/tmp/m-ui.log` 位于内存文件系统，超过约 128 KiB 后会裁剪为最近 200 行，且重启后清空。m-ui 还会写入路由器系统日志；系统日志的内存大小、持久化位置和轮转策略由路由器自身配置决定。

## 彻底断电后 ADB 被关闭

安装[ ADB Keeper](../android/adb-keeper/README.md)。安装后仍无法恢复时，依次检查：

1. 电视的已安装应用列表中是否有 `io.github.ylsislove.mui.adbkeeper`。
2. `WRITE_SECURE_SETTINGS` 权限是否因固件升级或重装而丢失。
3. 日志是否在冷启动早期出现“已在冷启动 ADB 窗口中优先启用 Keeper 无界面后台恢复”或“ADB Keeper 有限后台恢复已准备”。
4. `6095` 是否在冷启动后上线；短暂离线时它只用于在线判断和最终启动用户应用，连续离线至少 120 秒后才允许单次启动 Keeper 兜底。

Keeper 启动后会在 5、10、15、30、60、90 秒分别重写一次 ADB 设置，重试使用非唤醒闹钟，不会为了执行任务而点亮电视。如果 90 秒后仍未恢复，m-ui 继续低频检查；只有此前 `6095` 已连续离线至少 120 秒并重新上线时，才允许一次可能唤屏的 `6095 startapp` 兜底。可手动打开 ADB 检查权限和固件兼容性；手动恢复后 m-ui 会自动回到正常屏幕监控。

如果日志在同一次彻底开机中先短暂连接 ADB，数秒后又断开，这是部分小米固件的真实开机时序。`1.3.3` 会在这个窗口中准备 Keeper，并同时读取 display、power、启动原因和最近唤醒时间；静默重启时无论整机明确为 `Asleep`，还是处于 `reboot,quiet + Awake + ON + 0/0` 的启动假亮屏状态，都会按 `OFF` 处理，不会在物理黑屏时启动用户应用。

如果电视彻底断电后长时间不联网，Keeper 的有限重试可能在按遥控器前结束。m-ui 会记录 `6095` 的完整离线时长：连续离线至少 120 秒后重新上线且 ADB 仍不可用时，只通过 `6095` 单次唤起 Keeper。短暂静默重启不会触发；单次失败后需等下一次完整离线会话，不会循环唤屏。

不要把 `adb shell reboot quiet` 当作电视自身静默重启的等价模拟。已验证机型执行该诊断命令后，可能进入“面板只有很弱的黑色背光、桌面文字隐约可见、桌面或应用仍出声、遥控器电源键暂时无法恢复”的异常中间态，需要电视实体按键才能完全点亮。m-ui 从不执行任何重启命令；该现象只属于人工诊断测试，不需要为正常运行开启额外兼容逻辑。

如果固件从启动第一刻就不开放 ADB，同时又拦截 Keeper 的开机广播，则无界面方案无法自行恢复。此时只能手动打开 ADB，或选择会操作电视界面的恢复方式；m-ui 默认不采用后者，以免再次发生无人操作时电视被唤醒。

未安装 Keeper 时，m-ui 仍需要先观察到 `OFF`，再观察到 `ON`。如果电视亮屏时直接断电，恢复后可能不会触发。

## 收集诊断信息

报告问题时，请附上以下信息，但务必删除 IP、MAC、密钥等隐私内容：

```sh
uname -a
m-ui version
m-ui status
m-ui logs
/usr/lib/m-ui/m-adb --version
```

不要上传 `/etc/m-ui/adbkey`。
